# 客服聊天记录 · 会话级知识提炼（店小蜜 KB）

## Overview
把一个会话（客服聊天记录）里**能进知识库的内容**，用 LLM 理解**抽取**成「提炼前 / 提炼后」对照 CSV。**抽取优先、原话优先**：从多条聊天消息中抽取可复用问答并拼接成通顺文字，**若客服原话已合理通顺则尽量不改写，避免内容丢失**。逐批进行（默认每批 5 个会话），源数据只读不改、不清洗、不删。

本 skill 封装三件事：**① 可靠读源** ② **选批 + 导出原始对话** ③ **安全的 CSV 写出并防损坏**。
**真正的提炼判断由 LLM 在对话中完成**（见下方「提炼规则」）——脚本只做机械搬运与选批，**不替你做判断**。

## 何时使用
- 用户有 `客服聊天记录.xlsx` 或导出的 `8.3~.csv`，要"把能进知识库的聊天内容提炼出来"。
- 用户说"提炼下一批 / 批次N""从这堆聊天记录里提知识库条目"。
- 强调：**LLM 理解提炼，不是脚本规则**。脚本碰不到判断。
- ⚠️ **范围边界（重要）**：本 skill **完全自包含**，运行时**只使用本目录 `scripts/` 下的三个脚本**，禁止加载、引用或调用 `kb-extract`（及其 `redline.py` / `extract_runner.py` / `硬规则库.md`）。`kb-extract` 是文件级多 Agent RAG 方向（已对客服降级），与本会话级提炼任务**无关，不得触发**。

## 输入
- 聊天记录 CSV：`.../店小蜜/客服聊天记录_csv/8.3~.csv`（列：会话ID / 日期 / 时间 / 对象 / 发话者 / 消息 / 消息状态 / 商品ID / 商品；UTF-8 BOM）
- 或原始 xlsx：`.../店小蜜/客服聊天记录.xlsx`（含 sheet `8.3~`）
- **商品目录（绑定权威源）**：`.../店小蜜/商品ID.xlsx`（40 个商品ID / 36 个商品名，同一名对应多型号ID）；
  已预处理为 `.../店小蜜/客服聊天记录_csv/商品ID_映射.json`（`id2name` / `name2ids`），**「商品」列取值必须来自此处**。
- 输出目录：`.../店小蜜/客服聊天记录_csv/`（批次 CSV 与原始对话子集 CSV 都放这）

## 核心流程（每批）
1. **可靠读源**：若只有 xlsx，先 `scripts/extract_sheet.py <xlsx> [sheet] [out_dir]` 导出 `8.3~.csv`。
   ⚠️ 用 openpyxl **普通 `load_workbook`（非 `read_only`）**——`read_only` 对此文件会误读成 1 行。
2. **选批**：`scripts/select_next_batch.py <8.3~.csv> <输出目录> [--count 5]`。
   脚本自动跳过已做会话（扫描输出目录里 `知识提炼_批次*.csv` 收集 done 会话ID），挑 5 个：
   **3 个带商品（尽量不同产品）+ 2 个无商品**，且都有实质问答。把选中会话的**全部原始消息**写到
   `输出目录/批次N_原始对话.csv`（保留完整 9 列、不截断、不重排）供 LLM 用 Read 工具直接阅读，并打印摘要。
3. **LLM 提炼**：用 Read 工具读 `批次N_原始对话.csv`，按下方「提炼规则」逐会话理解，产出候选条目（每行 12 列）。
4. **安全写出**：把候选条目写成 JSON（用 Write 工具，结构见下），再
   `scripts/write_batch.py <rows.json>` 写出 `知识提炼_批次N.csv`（utf-8-sig），并**自动校验文件头非 PK（防 zip 损坏）**，损坏则自动从 zip 恢复重写。

JSON 结构：
```json
{"batch": 4, "out": "可选覆盖路径",
 "rows": [ {"批次":"4","会话ID":"...","商品":"...","提炼前_原始问答":"客户:... → 客服:...",
            "提炼后_问题":"...","提炼后_答案":"...","意图":"...","答案标签":"...",
            "适用对象":"...","优先级":"...","入库结论":"入库","备注":"..."}, ... ]}
```

## 列结构（12 列，固定顺序）
`批次, 会话ID, 商品, 提炼前_原始问答, 提炼后_问题, 提炼后_答案, 意图, 答案标签, 适用对象, 优先级, 入库结论, 备注`

- **批次**：数字（1,2,3…）
- **会话ID**：原始会话ID
- **商品**：精确产品绑定（见规则 A）。**必须以官方目录 `商品ID.xlsx`（已导出 `商品ID_映射.json`）中的「商品名」为准**，
  绝不得编造目录外的名字（如"护腰椅""沙发椅""智能床""换鞋凳"这类营销泛指词）。源 商品 列有值直接用；
  为空则从对话文本反推到**目录内最贴近的商品名**，备注"由会话内容推断(源商品列空)"。店级政策填 `通用`。
  真判断不了（目录内无任何可贴商品）填 `⚠️ 复核`。
- **提炼前_原始问答**：**审计与回查锚点**。以**抽取拼接**为主：从该条 Q&A 涉及的多条原始消息中**抽取有用内容并拼接成通顺文字**；若客服原话本身已合理通顺，则**尽量逐字照录、不做改写**。格式 `客户:<原话> → 客服:<原话>`。
  - 只允许：剔除套话/占位/空值行；多条相关消息拼接时用"→"衔接（如 `客户:安装容易不 → 客服:咱们是半安装 → 客服:收货后拧紧靠背四颗螺丝即可`）。
  - **禁止**：删减客服回复中的关键信息（政策结论、具体数值、步骤）；凭空补全客服没说的话；把单条已通顺的回复改写成另一种说法。
  - 若原始答复落在占位行（"请在客户端查看原始聊天记录"），**照录占位原文**，入库结论标 `⚠️复核`、备注说明内容丢失——**不要替客服"还原"**。
- **提炼后_问题**：**尽量还原用户原话**——若客户提问本身通顺，则照录、不改写；仅当问题由多条消息组成时才拼接使其通顺。可去掉型号（云朵椅/Y1/pro/蒂芙尼…）和口语杂词，但**保留语义完整**。例："要自己安装吗？怎么安装？""需要插座对吧？"
- **提炼后_答案**：**抽取并拼接、尽量少改写**——从客服的多条回复消息中抽取该问题的答复内容拼接成通顺答案；**若客服原回复本身已合理通顺，则尽量原样保留、不做精简**，避免内容丢失（政策结论、数值、步骤等关键信息必须完整保留）。
  - 仅当多条消息拼接后衔接不畅时，做**最小幅度的衔接性改写**（加连接词、合并碎片句），**不得删减关键信息**。
  - **绝不自行补充客服原话未提及的退货/运费/质保/优惠等政策结论**。客户问 A 客服答 A，答案只讲 A。
- **意图（必填 · 问题主题轴 · 开放分类）**：顾客**问了什么**——**开放定类，不预设固定枚举**。以问题实际内容为准，遇到新类型就新增类别，**不要为了套进旧类而强行合并不同主题**。
  - 初始可参考的常见类别（非封闭、可增删）：价格优惠 / 功能卖点 / 售后退换 / 安装使用 / 物流配送 / 规格尺寸 / 订单支付 / 库存有货 / 材质工艺 / 其他 —— 仅作起步参考，实际问题超出时自由定类（如「老人适配/适老需求」「发票税务」「定制改款」等新类）。
  - 分类粒度保持一致、互斥：同一会话同一子话题归一类，不要把多个不相关问题塞进一个意图。
  - 来源：店小蜜测试集 10 意图作为**初始参考**，非强制全集。**只看问题、不看答案**。
- **答案标签（必填 · 答案内容轴）**：这条**答案属于什么内容类型**——15 类：产品说明 / 尺寸规格 / 清洁保养 / 结构工艺 / 材质面料 / 需求识别 / 使用场景 / 安装指导 / 品牌介绍 / 价格议价 / 发货物流 / 质保售后 / 发票赠品 / 关怀祝福 / 越界拒答。
  来源：店小蜜「知识管理-策略配置.xlsx」**原生答案标签字段（入库必填，平台原生）**。**只看答案内容、不看问题**。

  ⚠️ **两轴正交（问 vs 答），允许且经常应当不同**；下面 6 对是"同概念在两轴的近义写法"（**意图开放定类后，这些只是常见示例，意图可超出此表自由命名**），按各自轴分别填、**不要强行统一**：
  | 意图（问题轴 · 开放） | 答案标签（答案轴 · 固定15类） | 同一条目示例 |
  |---|---|---|
  | 价格优惠 | 价格议价 | 问"能优惠吗" → 答案讲议价/活动 |
  | 物流配送 | 发货物流 | 问"什么时候发" → 答案讲发货 |
  | 规格尺寸 | 尺寸规格 | 问"多大" → 答案讲尺寸 |
  | 安装使用 | 安装指导 | 问"怎么装" → 答案讲安装步骤 |
  | 售后退换 | 质保售后 | 问"能退吗" → 答案讲质保/退换 |
  | 材质工艺 | 材质面料 | 问"什么材质" → 答案讲面料/工艺 |
  - 非近义对的正常跨轴（**看起来不同是正确的**）：问"适合老人吗"(意图=功能卖点) → 答案讲需求匹配(答案标签=需求识别)；问"官方旗舰店吗"(意图=品牌/渠道咨询) → 答案讲品牌(答案标签=品牌介绍)；问"能给老人定制吗"(意图=定制改款，开放新类) → 答案讲定制流程(答案标签=其他)。
- **适用对象**：老人本人 / 子女代问 / 内部客服（可并排如"子女代问/老人本人"）
- **优先级**：P0 / P1 / P2（P0=核心售后物流政策；P1=常用；P2=补充）
- **入库结论**：`入库` / `⚠️ 复核` / `不入库`
- **备注**：绑定依据 / 冲突提示 / 剔除原因等

## 提炼规则（LLM 判断，逐步套用）
**A. 商品精确绑定（走「商品」列，不进问题/答案文本）—— 以官方目录为唯一权威**
- **权威源**：店小蜜目录 `商品ID.xlsx`（位于 `.../店小蜜/`），已预处理为 `商品ID_映射.json`
  （`id2name`：商品ID→商品名；`name2ids`：商品名→多个ID）。**所有「商品」取值必须是该目录里的商品名**。
- **源 商品 列有值** → 该值即目录商品名，直接用；若源值带具体商品ID，把 ID 记到 `备注`（如"商品ID:716876591029"）。
- **源 商品 列空** → 扫对话文本是否点名具体商品，映射到**目录内最贴近的商品名**：
  - 客户说"云朵椅/Y1/常乐椅/如意椅/云朵沙发/助起沙发/头枕/护颈枕/洗澡椅/护理床/减压床/起身助力器/
    床边扶手/拐杖/助行器/护腰垫/凝胶枕/三人沙发…" → 取其目录名绑定，备注"由会话内容推断(源商品列空)"。
  - 客户只说营销泛指词（"护腰椅""沙发椅""椅子""智能床"）→ **不要照抄这些词**，要据上下文推断到具体目录商品
    （如"护腰椅"应落为 云朵椅 / Y1 / 常乐椅 / 如意椅 / YI多功能椅 之一）；推断不出则绑最接近目录椅类 + 备注"推断"，
    仍无法确定填 `⚠️ 复核`。
  - 客户聊的根本不在目录内（如"换鞋凳"）→ 不能硬绑，标 `⚠️ 复核` 并在备注说明"目录无此商品"。
- **多型号聚合（重点）**：目录里**同一商品名对应多个型号ID**（云朵椅=5个ID、Y1=2个、助起沙发=2个、洗澡椅=2个、
  护颈枕/凝胶枕各2个、床边扶手=2个…）；反之个别 ID 聚合了多个类目（如 690137447012 含起身助力器/床边扶手/马桶扶手）。
  **绑定只写到「商品名」粒度，不新建型号名**；具体型号差异（矮款/常规款/加长款…）留在问题/备注。
- **变体锚定（矮款 / 常规款 / 加长款 / 高款 / 加大款…）**：会话中只说变体词、未点具体商品时，
  回溯该消息**之前最近一次客户发送的商品链接（含商品ID）**，变体即该商品的**具体型号（同商品不同型号）**；
  商品列填该商品（目录名），"矮款/常规款"作为型号差异保留在问题或备注。若前面从未出现商品ID → `⚠️ 复核`（不是 `通用`）。
- **属性 vs 政策二分**：产品属性（安装方式 / 尺寸 / 材质 / 是否拆洗 / 颜色款式 / 承重 / 适用场景）
  → 绑推断商品；店级政策（发货时效 / 发货地 / 品牌控价不议价 / 运费险 / 七天无理由框架 / 上门取件平台设置）
  → 填 `通用`。
- 内容未点名且问题具体 → `⚠️ 复核`（不是 `通用`）。

**B. 抽取拼接优先；原话合理则不改写**
- 定位：从多条聊天消息中**抽取**该条问答的有用内容，**拼接**成通顺文字；**优先保留客服原话，避免内容丢失**。
- 例：客户问"云朵椅自己安装吗"，客服答"咱们是半安装，收货后只需要拧紧靠背的四颗螺丝就可以的~并且我们都是有附带安装工具的，非常简单与便捷，一个人独立操作也没问题的" → 提炼后_问题"要自己安装吗？怎么安装？"；提炼后_答案**基本照录原话**（仅去掉"咱们/亲亲~"等口语衬词，保留全部关键信息：半安装、四颗螺丝、附带工具、一人可操作）。
- ⚠️ **忠实性硬约束（不变）**：答案不得包含客服原话未提及的退货/运费/质保/优惠结论。曾发生把"颜色不符"答案
  擅自加"如不满意可走七天无理由"的编造——已禁。
- ⚠️ **内容保留优先（新增）**：抽取拼接时，客服回复里的**具体数值 / 政策结论 / 步骤顺序 / 材质名称**等关键信息必须完整保留，不得因"精简"而丢失。若一条回复已通顺完整，则**不做改写**。
- **意图 vs 答案标签（两轴正交）**：意图按"顾客问什么"**开放定类**（见列结构）、答案标签按"答案属什么内容"填且**固定为平台原生 15 类**（入库必填），二者**允许且经常应当不同**；
  近义对（价格优惠/价格议价 等 6 对，见「列结构」映射表，仅示例非封闭）按各自轴分别填，**不要因看起来该一样而强行统一**。

**C. 入库判定**
- `入库`：真实、可复用、合规、适用产品明确或通用。
- `⚠️ 复核`：① 关键答复落在占位行（"请在客户端查看原始聊天记录"）→ 内容丢失，判复核非入库；
  ② 适用产品不明确（且无法用变体锚定规则定位）；③ **同一会话内**客服口径自相矛盾（如先说可退后说不可退）
  → 标复核并备注矛盾，不私自合并。
  ⚠️ **跨会话 / 跨批次的一致性冲突（如"是否上门安装"不同会话相反）暂不做主动排查**——会话量大、难判断真伪，
  留待人工或后续统一口径阶段；仅当本批次内明显撞见时可在备注提一句，不阻断入库判定。
- `不入库`：① 客服"晒图返现 / 返赠"话术（违反对客铁律 #18 禁好评返现，整条剔除）；
  ② 动态库存（"灰色缺货"类，固化会过时误导）；③ 纯套话 / 纯占位 / 纯问候（无实质问答）；
  ④ **价格优惠 / 价格议价整类不入库**（问题主题为价格优惠/议价/能便宜吗/活动立减等价格相关，或 答案标签=`价格议价`）：价格相关答复由 AI 自动回答**不可控**，
  一律不进知识库——含活动立减、多件折扣、"品牌控价不议价"等议价答复。价格问题建议走店小蜜**转人工**策略由人工处理，不进 KB。

**D. 合规（强制卡点，非可选）**
- #18 禁返现：含返现 / 返赠诱导的整条剔除（结论=不入库）。
- #16 禁内部词：含内部系统名 / 岗位流转 / 成本 / 供应商的过程描述，改写为对客表述。
- **疾病宣称硬闸**：家具 / 枕头 / 按摩类**不得宣称治疗疾病**（治疗 / 治愈 / 根治 / 理疗 / 颈椎病 / 腰椎 / 腰疼 /
  腰痛 / 失眠 / 关节炎等），只能舒缓 / 辅助表述。
  → **写出后强制跑 `scripts/compliance_scan.py <批次.csv>`**，对命中的行必须改写去掉疾病宣称后才可 `入库`；
  该脚本只做关键词标记，是否真违规由你判断并改写。

## 提炼规则（续）：完整性优先
**E. 完整性优先（避免遗漏）**
- 目标：**尽量不漏**。凡会话中出现的、可能可复用的真实问答都提炼，不按类型预筛、不列"高优类型"。
- 拿不准 → 偏向 `入库` 或 `⚠️ 复核`，**不轻易 `不入库`**；`不入库` 仅留给明确违规
  （返现/返赠 #18、动态库存、纯套话占位）。
- 同一会话可拆多条（不同子话题各一条），宁多勿漏。

**F. 提炼前_原始问答 = 抽取拼接 + 原话优先**
- 该列是**审计与回查锚点**，用于对照溯源。
- **原话优先**：若该条 Q&A 的原始问答已通顺完整，则**逐字照录**，LLM 不得改写、概括、润色。
- **允许的拼接**：当一条问答分散在**多条消息**时，从这些消息中**抽取有用内容，用"→"拼接**成连贯文字，剔除套话/占位/空值行。拼接时不改动抽出的字词本身。
- **禁止**：删减关键信息（数值/政策/步骤）；补全缺失内容；把单条已通顺的回复改写成另一种说法。
- 若原始答复落在占位行（"请在客户端查看原始聊天记录"），该列**照录占位原文**，同时在 入库结论 标 `⚠️复核`、备注说明内容丢失——**不要替客服"还原"出一段话**。

## 推荐工作流：双 agent 并行提炼 + main 合并（提升召回、减少遗漏）
目标：两个独立 agent 各跑一遍提炼（最大化覆盖、互相补漏），main 只做合并整理、**不做提炼**。
1. **派发两个提炼 agent（互不参考）**：各加载本 skill，读同一 `批次N_原始对话.csv`，独立产出
   `知识提炼_批次N_agentA.csv` / `知识提炼_批次N_agentB.csv`（用 write_batch.py，JSON 里 `out` 指定各自路径）。
   两者都只待在 kb-chatlog-extract 内，互不读取对方结果。
2. **main 合并**：读取两份 CSV，按 (会话ID, 提炼后_问题) 去重/合并，对答案不一致的做裁定
   （取更忠实/更完整者），产出 consolidated `知识提炼_批次N.csv`（12 列，用 write_batch.py）。
   - **绑定裁定**：两 agent 常在「商品」绑定上分歧（尤其源商品列空时）。裁定以**对话文本最贴合**的为准——
     如客户明确说「沙发椅」则绑 `沙发椅`，不取另一 agent 的 `护腰椅(推断)`；答案冲突取更忠实且**去型号**者。
   - **去重**：用 `merge_two.py` 预合并后，务必对同会话近义问法（如 `椅套也想要` vs `椅子套也想要`、
     `两扶手内径(坐宽)多长` vs `两扶手内径多长`）做归一化去重，保留信息更完整的一条，避免重复行。
   - 可用 `scripts/merge_two.py <A.csv> <B.csv> <out.csv>` 预合并（自动去重 + 列出冲突待裁项），main 再据此定稿。
3. **合规卡点**：合并后跑 `scripts/compliance_scan.py <知识提炼_批次N.csv>`，修正疾病宣称命中行。
4. **范围**：main 与两个 agent 均只使用本 skill 的 scripts，禁止触达 kb-extract。

## 已知坑（必读）
- **CSV 写出后被外部机制转成 zip（PK 头）**：批次 2、批次 3 都中过。症状：后续读报 utf-8 解码失败、
  文件头字节为 `PK`。`write_batch.py` 已内置校验 + 从 zip 恢复（openpyxl 读 sheet1，`read_only=False`
  拿全 12 列，重写 utf-8-sig）。**每次写后必验证**。
- **openpyxl `read_only` 误读行数**：源 xlsx 必须用普通 `load_workbook`。
