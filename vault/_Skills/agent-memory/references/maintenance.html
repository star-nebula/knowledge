定期维护操作手册 ​

记忆文件不是写完就完事的。定期整理才能保鲜。

维护节奏 ​

每次会话结束 ​

操作文件说明
更新进度working/todo.md完成的任务打 [x]，更新「当前位置」
记录决策context/decisions.md有新决策才写，不用每次
同步计划working/plan.md有 plan 才更新

每个开发阶段完成 ​

操作文件说明
清理已完成条目working/todo.md把打勾超过 2 周的任务移到历史区或删除
归档 planworking/plan.md移至 archive/plan-{阶段名}.md 或直接删除
更新技术栈AGENTS.md如有新增依赖，更新技术栈表格
补充关键约定AGENTS.md本阶段沉淀的任何团队/项目级约定

每季度（3 个月） ​

操作文件说明
归档旧决策context/decisions.md超过 90 天的决策 → 移至 archive/decisions-YYYY-QX.md
审查技术栈AGENTS.md检查表格是否与 package.json/requirements.txt 一致
审查关键约定AGENTS.md删除已不再执行的约定，补充新的
检查僵尸文件整个 .memory/delete 3 个月未更新的 plan.md

存档策略 ​

.memory/
├── archive/                           # 历史存档（按季度）
│   ├── decisions-2026-Q1.md           # Q1 决策归档
│   ├── plan-用户认证模块.md            # 已完成阶段的计划
│   └── todo-2026-Q2-done.md           # 已完成任务清单
└── ... (当前文件)

归档原则：

  • 决策已落实到代码中 → 可归档（从 decisions.md 移除，保留在 archive/）
  • 计划对应的阶段已完成 → 可归档
  • 任务清单中所有条目完成后超过 2 周 → 可归档

不归档的情况：

  • 正在进行中的决策（还在讨论、可能反转）
  • 全局性的「宪法级」约定（如 API 格式规范）— 这些留在 AGENTS.md 中

常见问题 ​

Q: decisions.md 太长了怎么办？ ​

按分类拆分：decisions.md 只保留最近 90 天的，旧的按季度移入 archive/decisions-YYYY-QX.md。

Q: todo.md 的「已完成」区域越来越长？ ​

每个阶段结束后，把已完成条目移到 archive/todo-{阶段名}-done.md，只保留「进行中」和「未开始」。

Q: 怎么判断一条决策是否「已固化」？ ​

如果对应的代码已经写了、测试通过了、并且没有人在讨论推翻它，就是已固化。

Q: archive/ 目录会不会也膨胀？ ​

archive 的目的就是归档历史供回溯，不会无限增长。如果某份 archive 文件超过 2 年且确认不会再查，可以删除。
